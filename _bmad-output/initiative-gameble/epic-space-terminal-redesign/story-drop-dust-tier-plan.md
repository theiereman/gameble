## Intent

**Problem:** Story 8.6 removed every read of `catalog_card_seasons.dust_tier`, but the column, its check constraint `catalog_card_seasons_dust_tier_check`, its writes (publication, benchmark seed, fixtures) and the `Catalog::Dust` rules behind them remain. The release date now gives only the card's year and the sets (spec catalog-and-rarity.md); dust is gone from the design (AD-28).

**Approach:** The contract step of AD-28's expand/contract (AD-21): a strong_migrations-safe migration drops the check constraint and the column, `Catalog::CardSeason` ignores the column, and every write and every now-dead dust rule (`Catalog::Dust`, the draft preview's dust shares, its back-office table and copy) goes, with their tests.

## Design Notes

Deploy order (AD-21, Kamal; `bin/docker-entrypoint` runs `db:prepare` when the new web container boots, before Puma, while the old containers still serve). The code shipped before this story (8.6) still writes `dust_tier`: `Catalog::UpsertDraftCard`'s `CardSeason.create!` (import worker; Rails inserts every cached column) and `PublishSeason`'s `update_all`. So:
1. Before deploying, make sure no import run is running and nobody publishes a season (back-office); the window lasts until the old containers stop.
2. Deploy this commit: the migration runs once, through `db:prepare`. The new code ignores the column, so a new process booted before the migration ran is safe too.
3. A later story removes `ignored_columns` once every environment has run the migration (deferred-work.md).
If an import must keep running, an import step that fails in the window resumes under `Steam::RecoverStalledImportsJob` (AD-19) on the new code.
